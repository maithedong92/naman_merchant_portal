# [](#section/Introduction)Introduction

We understand the difficulties of handling both online and offline sales for your store and handling multiple processes such as the following:

-   Managing multiple menu sets.
-   Maintaining an up-to-date menu on both GrabMart and the Offline POS.
-   Punching in GrabMart order into your POS.
-   Missing orders in the order reconciliation.
-   Missing orders in payouts.

The GrabMart POS API enables you to integrate with GrabMart and perform the following actions:

-   **Eliminate manual entering of orders into your POS** - When a consumer places an order for your store on GrabMart, it is directly reflected in your POS, allowing your store crew to focus on fulfilling the orders and satisfying customers.
-   **Sync your store menu in real time** - Whenever you update your GrabMart menu with new items or mark an item as out-of-stock, these changes are updated on GrabMart automatically. This saves man-hours and reduces the probability of human errors involved in updating the content.
-   **Manage store campaigns** - You can easily manage your store's campaigns directly from the GrabMart POS.

## [](#section/Introduction/Key-takeaways)Key takeaways

After reading this documentation, you can:

-   Use the various GrabMart POS APIs to manage your store.
-   Create a request and pass it to Grab's authentication middle layer.
-   Manage your store's menus, orders, and campaigns.
-   [Troubleshoot](#tag/troubleshooting) some commonly found issues.
-   Resolve minor issues with the [frequently asked questions (FAQs)](#tag/faqs) section.

## [](#section/Introduction/Available-regions)Available regions

GrabMart is operating and is available in 8 countries (Singapore, Malaysia, Vietnam, Thailand, Philippines, Indonesia, Cambodia and Myanmar) and over 200 cities.

## [](#section/Introduction/Terminology)Terminology

1.  **Integration**: The process of connecting a partner’s POS system with GrabMart merchants via APIs to enable seamless operations.
2.  **Sandbox**: A test environment where partners can perform staging testing to validate the integration before moving to production.
3.  **Partner**: The POS system used by merchants integrated with GrabMart APIs to manage menus, orders, store, campaign and loyalty.
4.  **Merchant**: A GrabMart store onboarded on the Grab app platform and interacts with the partner’s POS system via API integration.

## [](#section/Getting-started/Integration-journey)Integration journey

#### 1\. Submit Form

-   Partners submit an interest [form](https://developer.grab.com/contact-us) to initiate the integration process by providing company details and contact information.
    -   Select **"Mart"** as the category.
-   Grab conducts a background check and reviews the submission for approval.

#### 2\. Development

-   Partners review the onboarding deck included in the staging project to visualize the integration process and understand how to get started.
-   Partners proceed to develop the integration based on the GrabMart API documentation provided.

#### 3\. Staging Test

-   Partners perform staging tests within the [developer portal](#section/Getting-started/Developer-portal) to validate product logic and ensure the integration works as intended. Any issues identified during testing are addressed before moving to production.

#### 4\. Production Test

-   Partners test the integration with a pilot store that has low traffic in a live production environment to ensure the integration operates correctly.

#### 5\. Phased Rollout

-   The integration is gradually rolled out to monitor stability and performance with real traffic.

## [](#section/Getting-started/Developer-portal)Developer portal

To streamline the initial integration phase, Grab has built a [developer portal](https://developer.grab.com/) equipped with testing tools and predefined test cases for basic API functionality validation. This simplifies the integration process and ensures smoother onboarding for partners.

The developer portal, also known as the sandbox. With the staging project created in the developer portal, you can:

-   Synchronise your menu with Grab's menu structure. There is also a built-in menu simulator tool that provides instant feedback.
-   Preview the menu rendered on the app simulator.
-   Test your menu by placing an order and verifying the order details in your POS machine.

> Please note that the Sandbox environment **may not** exactly replicate the Production environment, and there may be differences in behavior or functionality. It is recommended to thoroughly test in the Production environment before going live.

## [](#section/Getting-started/Outlet-mapping)Outlet mapping

Outlet mapping refers to the mapping of your outlet IDs in both GrabMart and partner databases. It is a crucial as incorrect outlet mapping may lead to missed GrabMart orders or orders being sent to the wrong outlet.

Partner can retrieve the Grab Merchant ID by:

-   Checking the merchant app
-   Extracting it from the query parameters in [GetMenu](#tag/get-menu-webhook/operation/get-menu-webhook) request during store activation
-   Requesting it from your integration support team

![Get GrabMart Outlet ID Sequence Diagram](/docs/img/grabmart-v2/mart-outlet-mapping.jpg)

Notes:

-   Outlet IDs, also known as Merchant IDs, are string values.
-   The Partner Merchant ID (External Store ID) refers to the store ID stored in partner's system and allows up to **64** characters.
-   Kindly reach out to your integration support team for store integration requests, as each country may have its own SOPs.

# [](#tag/api-best-practices)Best Practices: API

Follow these best practices to ensure efficient and seamless integration with the APIs:

#### 1\. Store Activation Required

-   Ensure the store integration is **activated** before making any Grab API calls to guarantee proper functionality.

#### 2\. Use the Correct Environment and URL Path

-   Verify that you are calling the APIs with the **correct environment** (e.g., sandbox, production) and the appropriate **URL path**.
    -   Incorrect configurations may lead to errors or failed requests.

#### 3\. Avoid Request Spamming

-   Do not send send **duplicate or repeated requests** in quick succession, as this may trigger rate limiting or result in blocked requests.
    -   A distributed interval lock is enforced for identical requests.

#### 4\. Handle Dynamic Fields

-   Ensure your integration is designed to handle **new or unknown fields** without disruptions.
    -   This ensures continued compatibility as we introduce enhancements or new features.

#### 5\. Integrate with Essential APIs

-   Integrate with the **essential APIs** to ensure a seamless integration experience.

#### 6\. Leverage the SDK

-   Utilize our official **SDK** to simplify the integration process and reduce potential errors.
    -   The SDK is designed to streamline API interactions and ensure compliance with integration standards.

# [](#tag/integration-requirements)Integration Requirements

To ensure a high standard of integration performance and reliability, partners are required to meet the following measurable quality requirements:

#### 1\. Error Rate

-   Maintain an error rate of less than **1%**, ensuring the reliability of the integration and delivering a seamless experience for all stakeholders involved.

#### 2\. Order Processing

-   Achieve **100%** processing for order submissions and order state updates, ensuring seamless order management.

#### 3\. Response Time

-   Respond to partner endpoints and webhook calls within **10 seconds** to avoid timeout errors.
    -   Partners are strongly encouraged to optimise their systems to meet the default response time for seamless communication.
    -   Partners may request an **extension** to increase the response time for specific endpoints or webhooks. However, please note that this adjustment will lead to a corresponding **reduction in the number of retry attempts**.

#### 4\. Monitoring and Alerts

-   Proactively monitor integration health and configure alerts for immediate action on errors to ensure uninterrupted operations.
    -   Accessible via the upcoming _**Health and Issue Hub**_ in the [developer portal](https://developer.grab.com/), offering direct insights into integration health and detected errors.

# [](#tag/http-resp-codes)HTTP response codes

It is crucial to always check the response code and take appropriate action based on the code received.

### Success codes

Code

Description

200 OK

Indicates that the request was successfully processed as expected.

204 No Content

Indicates that the request was successfully processed, but there is no content to return.

### Error codes

Code

Description

400 Bad Request

The request parameters are invalid or incorrectly specified. Verify and correct the request parameters before retrying.

401 Unauthorized

The authorization token is missing, invalid, or expired. Get a new token before retrying the request.

403 Forbidden

The request was rejected, probably due to a forbidden action. Check permissions and ensure the request is allowed.

404 Not Found

The requested resource does not exist. Confirm the resource exists and verify the endpoint URL.

409 Conflict

Indicates a process failure and common error, with details provided in the response.

429 Rate Exceeded

The request rate has exceeded the allowed limit. Reduce the request frequency and retry later.

500 Internal Server Error

A system or application error occurred. Retry the request. If the issue persists, contact support.

503 Service Unavailable

The server is temporarily unavailable due to maintenance. Wait and retry the request later.

# [](#tag/get-oauth-grab)Get GrabMart access token

All GrabMart API requests go through authentication checks. GrabMart uses OAuth 2.0 authentication for integration with all our partners.

# [](#section/Prerequisites)Prerequisites

Before you can use GrabMart APIs, you **must** onboard your application to Grab's platform.

![Get Access Token API Flow Diagram](/docs/img/grabmart-v2/mart-auth-grab.jpeg)

Steps:

1.  [Add OAuth2.0 client on Grab Platform Dashboard](#section/Add-OAuth2.0-clients-on-Grab-Platform-Dashboard).
2.  [Generate OAuth token](#section/Generate-OAuth-token) from Grab's authorisation system.
3.  Use generated OAuth token for [GrabMart API calls](#section/Sample-GrabMart-API-calls).

# [](#section/Add-OAuth2.0-clients-on-Grab-Platform-Dashboard)Add OAuth2.0 clients on Grab Platform Dashboard

1.  Select `Project details`.
2.  From the **OAuth 2.0 Clients** under `Credentials` section, click `Add` .
3.  Fill in the information.
4.  Click `Save`.
5.  The `client_id` and `client_secret` will then be auto-generated.

![Add oauth clients](/docs/img/grabmart-v2/add-auth-client.png)

# [](#section/Generate-OAuth-token)Generate OAuth token

Note:

-   Reuse generated tokens until they expire. The default expiration value is 7 days. Refer to the response parameter `expires_in`.
-   Request for a new token **only if**:
    -   Token has expired.
    -   You get a `401 Unauthorized` error.

Both `{{api-endpoint}}` and `<any-path>` are defined by your team. The first part of the URI, `{{api-endpoint}}`, can be replaced by any of your APIs. `<any-path>` is the dedicated path for GrabMart.

GrabMart will need to request for a new token if:

-   No token exists
-   Existing token is expiring
-   There is a `401 Unauthorized` response

# [](#tag/self-serve-activation-intro)Introduction

Self-serve Store Activation is a new store activation flow designed for our POS partners to ensure a smooth and hassle-free integration experience.

This feature is beneficial for those who rely on merchants to provide POS outlet and Grab outlet mapping information by enabling quick and efficient outlet integration with minimal human intervention. Upon adopting this integration, merchants will be able to:

-   Activate store integration **directly within the POS** system interface.
-   **Synchronize the Grab store menu** with the POS system during the integration process.

![Self-serve activation Diagram](/docs/img/grabmart-v2/ssa_diagram_flow.svg)

Notes:

-   The **[Push Grab Menu webhook](#tag/push-grab-menu-webhook/operation/push-grab-menu-webhook)** is **required** to be configured beforehand, regardless of whether there is a need to export the menu.
-   The **whitelist request** for merchantID(s) is **no longer required** for this self-serve activation flow.
-   Only **[selling-time-based menu](#section/Item-Selling-Time-Menu-structure)** is supported; section-based menus will not be able to proceed with integration activation.
-   Partners with legacy projects that have multiple partner codes may not be supported in this self-serve activation feature. Please reach out to your integration support team for confirmation.

  

💡 Important Announcement

The Self-Serve Activation Flow is mandatory for **3rd-party POS or Middleware partner** to integrate with **by the end of August 2025**. For **Enterprise Partners with Direct Integration**, it is optional particularly if you already have complete visibility of the outlets that need to be activated.  
  
⚠️ Please note that whitelist requests **will not be entertained** after the deadline.

## [](#section/Process-flow)Process flow

The following outlines the step-by-step process for merchants to initiate and complete the self-serve activation journey:

#### 1\. Merchant Initiates Journey

-   The merchant clicks a button implemented by the POS partner to start the integration process.
-   The POS system calls the Grab **CreateSelfServeJourney** endpoint to retrieve the redirect URL for the integration journey.

#### 2\. Merchant Login

-   In the webview, the merchant is prompted to log in to their Grab merchant account.
    -   Note: Only users with `Owner` or `Store Manager` roles can proceed with the integration journey.
-   Upon successful login, the Grab stores associated with the merchant account will be displayed.

#### 3\. Menu Export

-   The merchant is given the option to export the current Grab store menu to the POS system.
    -   If the merchant chooses to export, Grab pushes the store menu to the POS via the **PushGrabMenu** webhook.
    -   Alternatively, the merchant can skip this step and proceed directly to the next phase.

#### 4\. Enable Integration

-   The merchant proceeds with enabling the integration.
-   Grab calls the partner's **GetMenu** webhook to retrieve the latest menu from the POS system.

#### 5\. Integration Process

-   The integration process begins alongside the initial menu sync processing.
-   Grab pushes any integration status changes to the partner via the **PushIntegrationStatus** webhook.

  

> Note: Please be advised **not to validate** the Grab `merchantID` during the activation process. The respective `merchantID` will only be returned in the query parameters of the [GetMenu](#tag/get-menu-webhook/operation/get-menu-webhook) request. You may store this `merchantID` for mapping purposes and use it in subsequent menu synchronization requests.

# [](#tag/activation-best-practices)Best Practices: Activation

To ensure a successful and seamless store activation process, follow these best practices:

#### 1\. Prepare Menu for Initial Sync

-   The **first menu sync** will be initiated during store activation.
    -   The menu payload must be available and properly configured on the [GetMenu](#tag/get-menu-webhook/operation/get-menu-webhook) webhook before activation.

#### 2\. Endpoint Configuration

-   Ensure the **partner webhook** configuration is fully completed prior to store activation.

# [](#tag/sync-flow)Menu sync flow

The menu sync flow allows partners to update outlet menus on GrabMart in real time, whenever a change is needed.

![Menu sync flow diagram](/docs/img/grabmart-v2/mart-menu-sync-flow.png)

To make sure your menu changes are synchronised with GrabMart, follow these steps:

-   Action performed by partners:
    -   For minor changes like updating price or availableStatus, call the [Update menu record](#tag/update-menu-record) endpoint to make the relevant changes.
    -   For major changes to the menu, notify GrabMart and share the relevant outlet ID(s) by calling the [Update menu notification](#tag/update-menu-noti) endpoint.
-   Action performed by Grab:
    -   GrabMart calls the [Get Mart Menu Webhook](#tag/get-menu-webhook) endpoint for the relevant outlet ID(s) shared by partners to get the latest menu(s) and synchronises the changes in the GrabMart database accordingly.

Notes:

-   The menu sync could be **skipped** if there are **no changes** to the menu content compared to the previous cached menu record.
-   If the menu sync process is **unexpectedly taking a long time** and appears to be **stuck**:
    -   `QUEUEING`: This is likely due to high menu sync consumption latency. Wait for the system to process the job or retry after the lock is released in 3 hours.
    -   `PROCESSING`: If the status remains for an unexpectedly long duration, you may retry after 1 hour.

For further assistance, contact the integration support team.

# [](#tag/menu-best-practices)Best Practices: Menu

Follow these best practices to ensure optimal performance, accuracy, and efficiency when integrating your menu data:

#### 1\. Validate Menu Before Sync

-   Use the Menu Simulator tool to validate your menu payloads and prevent unexpected menu sync failures.

#### 2\. Schedule Full Menu Sync Wisely

-   Perform full menu sync only during **off-peak hours**, ideally **once a day**. Avoid frequent or unnecessary full menu syncs.
-   Full menu sync should primarily address menu edits, such as adding new items, removing items, or updating fields that are not supported via the [Update Menu Record API](#tag/update-menu-record).
-   Menu sync happens **asynchronously** and may take up to 30 minutes to complete, depending on the number of menu items in the outlet, the number of sync requests currently in the queue, and other factors.

#### 3\. Use Targeted Updates for Minor Changes

-   Use single or batch menu [updates](#tag/update-menu-record) for minor updates (e.g., `price`, `maxStock` or `availability`).
-   These updates are processed **in real-time**, unlike full menu syncs which are processed via a shared queue.

#### 4\. Avoid Redundant Full Menu Sync

-   Ensure the menu content has changed since the last sync before requesting a full menu sync. If **no changes** are detected, the request will be **skipped**.

#### 5\. Prevent Conflicting Edits

-   Avoid updating items via both APIs and the merchant app.
    -   Simultaneous edits from both sources can lead to **data conflicts or overwrites**.

#### 6\. Subscribe to Menu Sync Webhook

-   Integrate with the [menu sync state webhook](#tag/menu-sync-state-webhook) to receive status updates in real-time.
    -   This allows you to monitor menu sync health and quickly troubleshoot any menu sync errors.

#### 7\. Consistency Requirements

-   Do not make frequent changes to menu IDs and image URLs (such as adding timestamp query parameters). Keep menu IDs and image URLs consistent to minimize unnecessary updates and server load.
    -   If we detect this behavior, we may restrict or reject unnecessary menu changes to protect system performance.

### Selling Times

The `sellingTimes` represents the availability schedule for a category, subcategory or item within the menu. It allows partners to set when a particular item, subcategory or category is available. The selling time can be applied at the category, subcategory and item levels, providing greater flexibility for configuring the menu based on specific time periods.

#### Selling Times Overview

```
"sellingTimes": [
    {
        "startTime": "2022-01-09 00:00:00", //UTC time expected
        "endTime": "2025-01-09 05:00:00",
        "id": "sellingTimes_id",
        "name": "breakfast",
        "serviceHours": {
            "mon": {
                "openPeriodType": "OpenPeriod",
                "periods": [
                    {
                        "startTime": "08:00", //local time expected
                        "endTime": "13:00"
                    }
                ]
            },
            "tue": {...},
            "wed": {...},
            "thu": {...},
            "fri": {...},
            "sat": {...},
            "sun": {...}
        }
    }
]
```

The Selling Times feature follows these guidelines:

-   **Each outlet must have at least 1 and not more than 20 sellingTimes.**
    -   If less than 1 sellingTimes entry is provided in the array, an error will be returned.
    -   If more than 20 sellingTimes entries are provided, the system will truncate the excess entries.
-   **The selling time IDs should remain consistent and not swapped with each other.**
    -   Reuse the selling time IDs for subsequent menu syncs and avoid assigning new IDs unless there is a change to minimise unnecessary updates.
-   **The selling time duration (`sellingTimes[].startTime` and `sellingTimes[].endTime`) must be in UTC format.**
    -   Example: For a schedule starting on January 9, 2023, at 8:00 AM (UTC+8), `sellingTimes[].startTime` should be set as `"2023-01-09 00:00:00"`.
-   **Overlapping is allowed for the service hours periods across different selling times.**
    -   Specific time period selling time ~ Monday: `10:00 - 12:00`
    -   Regular menu selling tIme ~ Monday: `10:00 - 23:00`
-   **A maximum of 1 `sellingTimes` is allowed for each category, subcategory and item.**
    -   If no selling time is specified for an item, it will inherit the selling time from the subcategory, or from the category if not available; if a selling time is specified for the item, it will override the subcategory or category's selling time.
-   **Duplicates of `sellingTimes` with similar name, duration and service hour periods are not allowed.**
-   **Different `openPeriodType` can be applied for the selling time service hours (`sellingTimes[].serviceHours`)**
    
    -   `OpenAllDay`: Indicates the item is available 24 hours.
    -   `CloseAllDay`: Indicates the item is unavailable for the entire day.
    -   `OpenPeriod`: Defines availability for specific time periods. **Local time format** is expected. For example, `"08:00"`.
    
    -   A maximum of **3** periods can be defined per day for the service hours. Exceeding this will return an error.

> **ℹ️ Tip:** Utilise multiple periods within the service hours to align item selling times with different sessions.
> 
> -   If available only during morning session, configure the selling time with a single period: `08:00 – 11:00`.
> -   If available all day, configure the selling times with multiple periods: `08:00 – 11:00`, `12:00 – 17:00`, and `19:00 – 22:00`.

### Items

Items are the products that the outlets want to sell on GrabMart.

#### Items Overview

```
"items": [
    {
        "id": "item_id",
        "name": "item_name",
        "sequence": 1,
        "nameTranslation": {},
        "sellingTimeID": "sellingTimes_id",
        "availableStatus": "AVAILABLE|UNAVAILABLE|UNAVAILABLETODAY|HIDE",
        "description": "optional item description",
        "descriptionTranslation" : {},
        "price": 1000,
        "photos": ["<http://image_url>"],
        "specialType": "alcohol",
        "barcode": "<GTIN>",
        "maxStock": 10,
        "maxCount": 5,
        "weight": {
            "unit": "ml",
            "value": 200,
            "count": 5
        },
        "soldByWeight": true,
        "sellingUom": {  // for large order
            "len": 3.14,
            "width": 3.14,
            "height": 3.14,
            "weight": 500
        },
        "advancedPricing": {},
        "purchasability": {},
        "modifierGroups": [],
        "BCRSUnit": 1
    },
    ...

```

Items have the following rules:

-   **A category should have minimum 1, maximum 1400 items per subCategory**: If there is less than 1 item, you will get an error. If there are more than 1400 items, GrabMart truncates the rest.
-   Item name has a character limit of **80**.
-   Item description has a default character limit of **300** for all countries, except for `VN` with a custom limit of **2000** and `ID` with a custom limit of **500** characters. Any characters exceeding the limit will be truncated.
-   Item `price` is mandatory. If not provided, the price will be **set to 0** by default.
    -   For clarification on whether the menu price is inclusive or exclusive of tax, please refer to the [FAQs](#section/Menu/Is-the-menu-price-with-or-without-tax).
-   Item `availableStatus` defines the visibility on the Grab app platform and correlated with `maxStock`.
    -   For clarification on how each availableStatus is reflected and how maxStock impacts, please refer to the [FAQs](#section/Menu/What-is-availableStatus).
-   A maximum of **4** `photos` are supported per item.
    -   For image formats, please refer to the [FAQs](#section/Menu/What-are-the-required-formats-for-an-item-image).
-   Tag **alcohol** and **tobacco** items appropriately using the `specialType` to comply with legal and policy requirements.
    -   For more information on configuring price and availability by service type, please refer to the [FAQs](#section/Menu/What-happens-when-an-item-is-tagged-with-specialType-alcohol-or-tobacco).
-   Item `advancedPricing` and `purchasability` can be setup for different service types.
    -   For more information on configuring these, refer to the **Service Based Menu** [section](#section/Service-Based-Menu).

Notes:

-   An item may be marked as `UNAVAILABLE` if the **required** modifier groups and their associated modifiers are not available.
-   An item may be archived if its `name`, `description`, or `photos` fails the **content moderation check** due to policy violations, including but not limited to:
    -   Mention of competitor names or logos
    -   Containing personal information
    -   Presence of prohibited content
        
        > Please note that the item will remain archived until the moderation failed result is resolved. Refer to the [FAQs](#section/Menu/How-to-resolve-if-the-item-fails-the-content-moderation-check) for the solutions.
        

  

### Modifier Groups

Modifier Groups are the different options that a consumer can select within an item.

#### Modifier Groups Overview

```
"modifierGroups": [
    {
        "id": "modifier_group_id",
        "name": "modifier_group_name",
        "sequence": 1,
        "nameTranslation": {},
        "availableStatus": "AVAILABLE|UNAVAILABLE|UNAVAILABLETODAY|HIDE",
        "selectionRangeMin": 0,
        "selectionRangeMax": 1,
        "modifiers": []
    },
    ...
]
```

Modifier groups have the following rules:

-   **An item should have maximum 30 modifier groups**: If there are more than 30 modifier groups, GrabMart truncates the rest.
-   Modifier group names have a character limit of **50**.
-   Modifier Groups can be set as **optional and required**. Refer to [FAQs](#section/Menu/What-does-the-selection-range-do) for more info.
-   The modifier group IDs should remain consistent and be reused for subsequent menu syncs, unless there is a change, to minimize unnecessary updates.

  

### Modifiers

Modifiers are the selections within a modifier group.

#### Modifiers Overview

```
"modifiers": [
    {
        "id": "modifier_id",
        "name": "modifier_name",
        "sequence": 1,
        "nameTranslation": {},
        "availableStatus": "AVAILABLE|UNAVAILABLE|UNAVAILABLETODAY|HIDE",
        "price": 30,
        "barcode": "GTIN",
        "advancedPricing": {},
        "BCRSUnit": 1
    }
]
```

Modifiers have the following rules:

-   **A modifier group should have maximum 100 modifiers**: If there are more than 100 modifiers, GrabMart truncates the rest.
-   Modifier names have a character limit of **40**.
-   Each modifier can only be selected **once**, but multiple modifiers can be chosen within the same modifier group. For example, if the modifier group is Select Two Drinks, the consumer can select 1 coke and 1 water, but not 2 cokes.
-   The modifier IDs should remain consistent and be reused for subsequent menu syncs, unless there is a change, to minimize unnecessary updates.

# [](#tag/order-types)Order Types

## [](#section/Order-Acceptance)Order Acceptance

The store can be configured as Manual Acceptance or Auto Acceptance on the GrabMart internal system.

```
{
    ...
    "featureFlags": {
        "orderAcceptedType": "<AUTO|MANUAL>"
    },
    ...
}
```

-   `MANUAL` The store needs to accept the order via the [Accept/Reject Order endpoint](#tag/accept-reject-order).
-   `AUTO` No action is needed to accept the order. The order is automatically accepted on GrabMart and submitted to the partner.
    -   If an order cannot be fulfilled, the partner has the option to [edit](#tag/edit-order/operation/edit-order) or [cancel](#tag/cancel-order/operation/cancel-order) the order.

Note: All new partners should have **auto order acceptance enabled**, where orders are automatically accepted, eliminating the need for the partner to manually accept or reject orders.

## [](#section/Delivery-On-Demand)Delivery On Demand

```
{
    ...
    "featureFlags": {
        "orderType": "DeliveredByGrab"
    },
    ...
}
```

-   The order is delivered by the Grab driver.
-   By default, the order is submitted after a driver is allocated.
    -   Orders submitted upon driver allocation will not have the `DRIVER_ALLOCATED` state pushed.
-   However, there might be a **delay in driver allocation**, considering factors like store busy mode, order preparation time and etc. In such cases, the order will be submitted **upon creation**, with driver allocation occurring as the estimated order ready time approaches.
-   Partners may [Mark Order Ready](#tag/mark-order-ready) to notify the driver when the order is ready.
    -   This may trigger driver allocation if the driver has not been assigned yet, while the order is ready to be collected.

## [](#section/Take-Away-Self-Pick-Up)Take Away / Self Pick-Up

```
{
    ...
    "featureFlags": {
        "orderType": "TakeAway"
    },
    ...
}
```

-   Users collect the order directly at the store.
-   The order is submitted immediately upon order creation.
-   Only the following order states will be sent to the partner: `DELIVERED` and `CANCELLED`.
-   The order is automatically marked as completed after **2 hours**.

## [](#section/Delivery-by-Store)Delivery by Store

```
{
    ...
    "featureFlags": {
        "orderType": "DeliveredByStore"
    },
    "receiver": {
        ...
    }
```

-   The order is submitted immediately upon order creation.
-   A delivery status update is required from the partner via [Update Delivery State](#tag/update-delivery-state).
-   Only the following order states will be sent to the partner: `COLLECTED`, `DELIVERED` and `CANCELLED`.
-   The order will be automatically marked as completed after a specific configurable period.

It typically occurs for a **large order**, with the evaluation performed by our data science model. In such case, the order will be split amongst 2 riders to minimize cancellations and improve fulfillment rates.

```shell
    ],
    "promos": [
        // same for both payloads regardless of which one is applied
    ]

```

```shell
    "orderID": "102992157-C6NKLTAACKDGBE-2",

    "items": {
        // respective items details after the split
    }
    "price": {
```

# [](#tag/order-best-practices)Best Practices: Order

To ensure a smooth and efficient integration, please follow these guidelines when handling order-related APIs:

#### 1\. Ensuring Accurate Webhook Acknowledgment

-   The partner webhook should only return a `2XX` HTTP status code if the order request has been **successfully** received and synced to your POS system.
    -   Avoid returning 2XX for requests that fail internally, as this may result in incorrect assumptions of successful sync on our end.

#### 2\. Handling Order Updates

-   An order with the same `orderID` should be treated as a single order, not as a duplicate.
    -   Grab may resend the order due to **edits or recalculations**, which can be identified using the `isMexEditOrder` flag.
    -   Partner should not reject these requests, as they contain the latest and most accurate order details.

#### 3\. Recover Missing Orders via the List Orders API

-   If you encounter missing orders that were not synced to your POS, you can use the [List Orders API](#tag/list-order) to retrieve them:
    -   Supports filtering by `orderIDs` or `date` and returns data for the past 30 days.
    -   Please be noted that the data may be **cached for up to 30 minutes**, so this is not suitable for real-time order retrieval.

#### 4\. Implement the Mark Order Ready API

-   We strongly recommend integrating the [Mark Order Ready API](#tag/mark-order), which provides multiple benefits:
    -   Notifies the driver that the order is ready, reducing waiting time.
    -   Enhances our data science models for estimating order preparation time. Accurate preparation times lead to a better customer experience and more efficient deliveries.
    -   Triggers driver allocation earlier if delay allocation is enabled due to an initially long preparation time estimate.

# [](#tag/submit-order-webhook)Submit order webhook

When a consumer places an order from integrated merchant, GrabMart calls the partner's submit order webhook endpoint, sending the order details in the request payload. This webhook is crucial for ensuring that orders placed on the GrabMart platform are seamlessly submitted to the partner's POS system for processing.

![Submit order diagram](/docs/img/grabmart-v2/submit-order.png)

You can replace the first part of the URI, `{{api-endpoint}}`, with any of your APIs. `<any-path>` is the dedicated path for GrabMart.

Note:

-   If the `isMexEditOrder` value changes from false to true, this submit request is not considered a duplicate request.
    -   It indicates that the order was **edited or recalculated**, and does not necessarily mean the order was edited by the merchant.
-   If the same items are ordered with different modifiers selected, it will be treated as separate items in the request payload.
-   Only merchant-funded `campaigns` and `promos`, whether fully or partially funded, will be included in the payload.
-   In accordance with the policy, the values of `deliveryFee`, `basketPromo`, `grabFundPromo` and `eaterPayment` will be removed and set to `0`, except when `paymentType: CASH` and `orderType: DeliveredByStore`.
-   The `virtualContact` remains **valid for 6 hours** from the order creation time `orderTime`, but for scheduled orders, it starts from the order submission time `submitTime`.
    -   If the `virtualContact` is `UNAVAILABLE`, merchants can use the **chatting** or **calling** features available in the merchant app as an alternative option.
    -   For more information about how the virtual contact works, see the [FAQ](#section/Order/How-to-contact-customer-using-the-virtual-contact).

# [](#tag/push-order-state-webhook)Push order state webhook

The Push Order State Webhook allows GrabMart to send order status updates to the partner via a request. It ensures partners are promptly notified of any changes in order status. This webhook is crucial for efficient order management.

![Update order state diagram](/docs/img/grabmart-v2/push-order-state.png)

You can replace the first part of the URI, `{{api-endpoint}}`, with any of your APIs. `<any-path>` is the dedicated path for GrabMart.

## [](#section/Order-states)Order states

These are the different order states that may be used:

-   `DRIVER_ALLOCATED` - Driver has been allocated
-   `DRIVER_ARRIVED` - Driver has reached your store to collect the order
-   `COLLECTED` - Driver has collected the order from your store
-   `DELIVERED` - Driver has delivered the order to the consumer location
-   `CANCELLED` - Order has been cancelled by the consumer, merchant, or driver for some reason, Refer to `message` for more information.
-   `FAILED` - The order might fail because of unallocation, reallocation, system issues, etc. If there is a system issue, GrabMart will flag the order, and escalate if the issue is on your side. Refer to `message` for more information.

Note:

-   For **TakeAway** and **DineIn** orders, only the `DELIVERED` and `CANCELLED` states are applicable.
-   For **DeliveredByStore** orders, only the `COLLECTED`, `DELIVERED`, and `CANCELLED` states are applicable.
    -   These states are only pushed when the [reportDeliveryState](#tag/delivery-state) API request is received from the partner.
-   The `DRIVER_ALLOCATED` state will not be sent when the order is submitted upon driver allocation.

# [](#tag/cancel-order)Cancel order

Partners can call this GrabMart endpoint to cancel an order. There is a country-level configuration on the order cancellation limits for daily, weekly and monthly. If the respective daily/weekly/monthly limits are approaching after an order is successfully cancelled, this endpoint returns the nearest remaining cancellation limits.

Orders with the order types `DeliveredByStore` and `Scheduled Order` may be cancelled before the `DRIVER_ALLOCATED` state. Other than that, an order can be cancelled only **after** a driver is allocated.

Notes:

-   Cancellation of scheduled orders is now supported for certain countries: `TH`, `MY`, `PH`, `ID`, `SG` and `VN`.
-   Cancellation of self-pick up orders is now supported for certain countries: `MY`, `PH`, `TH`, `VN`, `KH` and `MM`.
-   Partner can check the order cancellability by calling [Check Order Cancellable API](#tag/check-cancelable).
-   The order cancellation limit is shared between the API and the merchant app.

# [](#tag/pause-store)Temporarily pause store

This GrabMart endpoint allows partners to pause or unpause their store on GrabMart. Partners can only choose to pause their store for:

-   30 minutes
-   1 hour
-   24 hours

Notes:

-   Sending a pause or unpause request while the store is already in the same status will result in a conflict error.
-   Partner can perform the pause using merchant app or reach out to integration support team if longer pause is needed.
-   Partners can call this endpoint to unpause the store if they wish to unpause it before the end of the pause period.
-   The store will automatically resume operations once the specified pause duration has elapsed.
-   The store may be paused if **no items are available**. Please ensure at least **one** item is available before performing the unpause operation.

# [](#tag/campaign-type)Campaign type

Campaign API supports six types of campaigns that offer varying levels of discounts: `Dollar off`, `Percentage off`, `Target price`, `Bundle offer`, `Delivery fee off` and `Free item` . Each campaign type is designed to meet specific marketing needs and offers different discount structures to help drive customer engagement and sales. You can choose the campaign type that best suits your business goals and implement it seamlessly through our API.

Notes:

-   The same item(s) cannot be included in more than one campaign during the same time period.
-   Only one free item campaign is allowed for the same period.
-   A [free item campaign](#section/Free-item-campaign) cannot overlap with an order-level discount campaign, and vice versa. However, it can overlap with a [delivery fee discount campaign](#section/Delivery-fee-off-campaign).
-   Concurrent create/update campaign operations for the same merchant are not allowed. Ensure requests are processed sequentially to avoid conflicts.

## [](#section/Dollar-off-campaign)Dollar off campaign

-   `Item dollar off` - Net discount for selected item(s).
-   `Category dollar off` - Net discount for selected category.
-   `Order dollar off` - Net discount for entire order.

-   Item dollar off
-   Category dollar off
-   Order dollar off

```shell
----- $3 off for selected item(s) (Item Dollar Off) -----
{
    ...
    "discount": {
        "type": "net",
        "value": 3,
        "scope": {
            "type": "items",
            "objectIDs": ["<item_id_1>", "<item_id_2>", ...]
        }
    }
}
```


# [](#tag/campaign-best-practices)Best Practices: Campaign

To ensure a reliable and effective campaign integration experience, please follow these best practices when using the Campaign APIs:

#### 1\. Test Create Campaign Requests in Sandbox

-   Before creating campaign(s) in production, it's recommended to test your request payload in the sandbox environment.
    -   This helps prevent errors caused by invalid parameters or unforeseen structural issues.

#### 2\. Sync Menu Items Before Creating Campaigns

-   Ensure the targeted item(s) are **valid and synced** to the menu before creating campaigns to prevent _item not found_ errors.
    -   Avoid changing the item `id` after a campaign has been created, as this may trigger item recreation and invalidate any existing linked campaign(s).

#### 3\. Implement Proper Error Handling and Retry Logic

-   Avoid retrying campaign creation requests blindly.
    -   Always check the error message returned in the Create Campaign API response for any errors or validation issues.

# [](#tag/loyalty-webview-best-practices)Best Practices: Loyalty (Webview)

Follow these best practices to ensure a reliable and effective loyalty integration experience when using the Loyalty APIs (Webview):

#### 1\. Membership Unlinking from Partner/Offline

-   When a customer deletes or unlinks their membership account on your platform (not through Grab), call Grab's [Notify Membership endpoint](#tag/notify-membership-webview) with `UNLINK` value.
    -   This ensures Grab removes the linking between the Grab user account and partner membership account.
-   If you do not send a request to Grab, the membership remains linked and is validated during the customer's next purchase. As a fallback, return response code `200` with `INVALID` status in the subsequent [Get Membership Detail](#tag/get-membership-webview) request from Grab.
    -   These are the only ways to unlink membership when the membership or linkage is no longer valid on your side.

#### 2\. Onboarding and Testing

-   Loyalty Webview does not support self-serve testing. Collaborate with Grab's integration team to perform testing.
-   The high-level onboarding flow includes:
    -   Introduction and alignment
    -   Development phase and SIT

-   To access loyalty-related endpoints, include the required API scope when requesting your API access token. For more information, see [Get GrabMart Access Token](#tag/get-oauth-grab).

# [](#section/Currency)Currency

## [](#section/Currency/What-does-exponent-mean)What does exponent mean?

Exponent refers to the number of times we need to multiply the major unit by a log base of 10, in order to get the minor unit. Example: A price of 100 means 1 dollar with an exponent of 2.

# [](#section/Menu)Menu

## [](#section/Menu/How-do-I-sort-the-categoryitemmodifier-groupmodifier)How do I sort the category/item/modifier group/modifier?

Use the `sequence` field in each object to control the display order on the Grab app. Items with lower sequence numbers appear first, allowing you to strategically position important content.

**Best practices for sequence ordering:**

-   `categories` - Position new or promotional categories at the top (lower sequence values) for maximum visibility.
-   `items` - Feature best-selling items first to improve conversion rates.
-   `modifierGroups` - Order modifier groups strategically to optimize conversion and Average Order Volume (AOV).
-   `modifiers` - Arrange modifiers to guide customer selection and increase AOV.

> **Important:** Always include the `sequence` field in your menu JSON to ensure items display in your intended order. Without it, the ordering may be unpredictable.

## [](#section/Menu/What-is-availableStatus)What is availableStatus?

This parameter indicates the availability of a category, a subcategory, an item, a modifier group or a modifier.

For example, if your store runs out of an item, you can set `availableStatus` to `UNAVAILABLE` for the item. However, if the item is temporarily out of stock only for the duration of the day, you can set `availableStatus` to `UNAVAILABLETODAY` for the item.

Status

Description

AVAILABLE

Visible and able to select from the menu.

UNAVAILABLE

Visible but greyed out and unable to select from the menu.

UNAVAILABLETODAY

Visible but greyed out and unable to select from the menu by the end of the day. It will be available next day onwards.

HIDE

Invisible and hidden from the menu.

Note: In order to set an item as "UNAVAILABLE", it is required to update both the `availableStatus` and `maxStock` fields, whereby the `maxStock` value should be set to 0. Item will be set to "AVAILABLE" if `maxStock` > 0.

## [](#section/Menu/Should-the-ID-be-unique)Should the ID be unique?

Yes, all IDs must be unique.

## [](#section/Menu/Is-the-menu-price-with-or-without-tax)Is the menu price with or without tax?

The menu price can be either with or without tax, based on the country configuration:

-   The menu price is exclusive of tax, with a separate tax rate configured in our system.
-   The menu price is inclusive of tax, with the tax rate set to 0. This applies to `SG`, `TH`, `VN` and `PH`.

Please contact the integration support team for assistance with tax configuration setup or any other inquiries.

## [](#section/Menu/What-are-the-required-formats-for-an-item-image)What are the required formats for an item image?

-   Provide HTTP(s) URLs for the images.
-   Item images should have a **1:1 aspect ratio**. The maximum dimension is **4000x4000** pixels.
-   Image file sizes limit **2MB**. Image files larger than 2MB will not be displayed.
-   Valid image **file extension**
    -   For example: `jpg`, `jpeg`, `png`, `webp`
-   Recognisable **Content-Type** in the response header
    -   For example: `image/png`, `image/jpg`, `image/jpeg`, `image/webp`

Notes:

-   Update the image URL **only when the image changes**; otherwise, keep it consistent across the syncs to avoid unnecessary updates.
-   Ensure the image **follows the required format**. Failure to comply will result in image validation errors, and the image will not be added to the item.
-   Ensure the image URL is **accessible**. Grab will fetch the image from your CDN and update the database whenever the image URL changes.

## [](#section/Menu/How-to-resolve-if-the-item-fails-the-content-moderation-check)How to resolve if the item fails the content moderation check?

Review the item name, description or image and make necessary updates if needed. If it's a false positive, you may request an appeal by following these steps:

-   Use the appeal link provided in the email sent to the store PIC.
-   Request the integration support team to manually appeal.

> Note: The item will remain archived until the moderation failed result is resolved.

## [](#section/Menu/What's-specialType)What's specialType?

This is an optional tag used to classify specific regulated items, such as `alcohol` or `tobacco`. When the item is tagged, Grab applies specific restrictions to ensure the item complies with legal and policy requirements.

If `specialType` is set to `alcohol` or `tobacco`:

-   The item does not appear in the cross-sell checkout section.
-   The item does not get promoted in the "Recommended for you" section.
-   There is an explicit legal age consent when consumers try to check out with that item.

> Note: The merchant(s) **must be enabled for alcohol or tobacco sales** in order to sell items tagged with the special type `alcohol` or `tobacco` respectively. Please reach out to your integration support team for this setup.

## [](#section/Menu/What-does-the-selection-range-do)What does the selection range do?

The selection range controls the number of selections a consumer can make. This parameter has three different values:

-   Optional - If modifier group is optional, `selectionRangeMin` **must be** zero.
-   Mandatory - If modifier group is mandatory, `selectionRangeMin` must be greater than or equal to 1.
-   `selectionRangeMax` can be used to set the maximum number of modifiers a consumer can select.

## [](#section/Menu/If-a-modifier-runs-out-of-stock-can-I-mark-it-out-of-stock-on-GrabMart)If a modifier runs out of stock, can I mark it out of stock on GrabMart?

Yes, it is definitely possible. Just set the `availableStatus` for that modifier to UNAVAILABLE, and it gets greyed out on the app, so consumers cannot choose that modifier.

## [](#section/Menu/Can-the-price-of-a-modifier-be-zero)Can the price of a modifier be zero?

Yes, it can be zero.

## [](#section/Menu/How-do-I-set-up-BCRS-for-items-and-modifiers)How do I set up BCRS for items and modifiers?

**For Singapore only.** The Beverage Container Return Scheme (BCRS) is a deposit-refund scheme for beverage containers. You can specify the number of BCRS containers for items and modifiers using the `BCRSUnit` field during menu sync.

**Key points:**

-   `BCRSUnit` accepts integer values representing the number of beverage containers.
-   Only values greater than 0 are valid. Setting `BCRSUnit` to a positive value will apply the BCRS deposit to that item or modifier.
-   Setting `BCRSUnit` to 0 or omitting the field will remove any existing BCRS value from the item or modifier.
-   The BCRS deposit amount is automatically calculated based on the configured rate in the system.

**Example usage:**

```
"items": [
    {
        "id": "ITEM-1",
        "name": "Coke 330ml",
        "price": 250,
        "BCRSUnit": 1,
        ...
    },
    {
        "id": "ITEM-2",
        "name": "6-Pack Coke",
        "price": 1200,
        "BCRSUnit": 6,
        ...
    }
]
```

For modifiers with beverage containers, add `BCRSUnit` at the modifier level:

```
"modifiers": [
    {
        "id": "MODI-1",
        "name": "Extra Coke 330ml",
        "price": 250,
        "BCRSUnit": 1
    }
]
```

> Note: The `BCRSUnit` field is only applicable for Singapore merchants participating in the BCRS program. Please contact your integration support team if you need assistance with BCRS setup.

> Note: This applies only to merchants with tax configuration set up. If tax is not configured and the menu sent is tax-inclusive, the tax will be sent as 0.

## [](#section/Order/How-can-I-retrieve-the-order-received-throughout-a-specified-period)How can I retrieve the order received throughout a specified period?

You can access the order records up to 30 days using [List orders](#tag/list-order) endpoints. If you need an older record, please contact your integration support team.

## [](#section/Order/How-is-the-price-adjustment-handled-after-an-order-is-edited)How is the price adjustment handled after an order is edited?

The consumers will be charged only after the order is completed, based on the final order amount. Any adjustments made to the order will be reflected in the final charge.

## [](#section/Order/What-is-the-retry-mechanism-if-the-Submit-Order-and-Push-Order-State-webhook-API-request-fails)What is the retry mechanism if the Submit Order and Push Order State webhook API request fails?

There will be 4 attempts for both requests. The initial retry will occur within 500 milliseconds, and for subsequent retries, the maximum interval will be 5 seconds.

## [](#section/Order/How-is-the-merchantFundPromo-split-across-the-sub-orders)How is the merchantFundPromo split across the sub-orders?

The `merchantFundPromo` amount is split based on the order value from the sub-order and the calculation may involve some additional Grab fees (if applicable) applied to the order, which is not exposed to the partner. However, partner may sum up the split amounts, which will equal the actual `merchantFundPromo` amount for the order. Additionally, the `merchantFundPromo` is derived from the `deductedAmount` in `campaigns[]` and the `mexFundedAmount` in `promos[]`.

## [](#section/Order/How-to-contact-customer-using-the-virtual-contact)How to contact customer using the virtual contact?

The virtual contact will be provided in both the [SubmitOrder](#tag/submit-order-webhook) and [ListOrder](#tag/list-order) payload under `receiver` object. The merchant can dial the provided `phoneNumber`, and during the call, they will be prompted to enter the `PIN`.

-   If the entered `PIN` is correct, the call will be successfully routed to the customer.
-   However, if the `PIN` is incorrect, the call will be terminated with an error message, but the merchant can still retry.
